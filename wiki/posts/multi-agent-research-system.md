# How we built our multi-agent research system (2025-06-13)

> **한 줄 요약:** Claude의 Research 기능은 리드 에이전트가 서브에이전트들을 병렬로 띄워 조사하는 orchestrator-worker 구조다. 성능의 핵심은 "충분한 토큰을 쓰게 하는 것"이고, 대가는 높은 비용과 조율의 어려움이다.

## 핵심 주장

1. **조사는 멀티 에이전트에 잘 맞는다.** 조사는 필요한 단계를 미리 알 수 없는 열린 문제라서, 한 번에 끝나는 선형 파이프라인으로는 처리할 수 없다.
2. **검색의 본질은 압축이다.** 서브에이전트가 각자의 컨텍스트 창에서 다른 측면을 동시에 탐색한 뒤, 중요한 토큰만 추려서 리드 에이전트에 넘긴다.
3. **성능은 토큰 사용량이 좌우한다.** BrowseComp 평가에서 성능 차이의 95%를 세 요인이 설명했다. **토큰 사용량 하나가 80%**이고 나머지는 도구 호출 수와 모델 선택이다. 컨텍스트 창을 나눠 쓰는 구조가 곧 토큰 용량을 늘리는 방법이다.
4. **대가가 크다.** 에이전트는 채팅보다 약 **4배**, 멀티 에이전트는 약 **15배** 토큰을 쓴다. 그만큼 가치가 높은 작업에만 경제성이 있다.
5. **안 맞는 영역도 있다.** 모든 에이전트가 같은 컨텍스트를 공유해야 하거나 의존성이 많은 작업은 맞지 않는다. 대부분의 코딩이 여기에 해당한다. 병렬화할 수 있는 부분이 조사보다 적기 때문이다.

## 수치

| 항목 | 결과 |
|---|---|
| 멀티 에이전트 (Opus 4 리드 + Sonnet 4 서브) vs 단일 Opus 4 | 내부 리서치 평가에서 **90.2% 향상** |
| 병렬화 (서브에이전트 3~5개 동시 + 각자 도구 3개 이상 동시) | 복잡한 질문의 조사 시간 **최대 90% 단축** |
| 도구 설명을 에이전트가 스스로 고침 | 이후 작업 완료 시간 **40% 단축** |

## 구조

```
 사용자 질문
   ▼
 LeadResearcher ── 계획을 Memory에 저장 (컨텍스트가 넘쳐도 계획은 유지)
   ├─▶ Subagent A ─ 웹 검색 + interleaved thinking ─┐
   ├─▶ Subagent B ─ ...                             ├─▶ 결과 종합 → 더 조사할지 판단
   └─▶ (필요한 만큼)                                ─┘
   ▼
 CitationAgent ── 주장마다 출처 위치 표시
   ▼
 최종 보고서
```

정적인 RAG(질문과 비슷한 조각을 가져오는 방식)와 달리, 여러 단계에 걸쳐 검색하며 새로 알게 된 것에 맞춰 방향을 바꾼다.

## 프롬프트 원칙 8가지

1. **에이전트처럼 생각하라.** 실제 프롬프트와 도구로 시뮬레이션을 돌리고 단계별로 지켜보면 실패 유형이 바로 보인다.
2. **위임하는 법을 가르쳐라.** 서브에이전트에게는 목표, 출력 형식, 사용할 도구와 출처, 작업 경계를 줘야 한다. 지시가 모호하면 일이 중복되거나 빈틈이 생긴다.
3. **복잡도에 맞게 노력을 조절하라.** 단순 사실 확인은 에이전트 1개에 도구 호출 3~10번, 비교는 서브에이전트 2~4개, 복잡한 조사는 10개 이상. 초기에는 간단한 질문에 서브에이전트를 50개씩 띄우는 실수가 있었다.
4. **도구 설계와 선택이 결정적이다.** Slack에만 있는 정보를 웹에서 찾으면 처음부터 실패한다. 도구마다 목적이 뚜렷하고 설명이 명확해야 한다.
5. **에이전트가 스스로 개선하게 하라.** Claude 4는 실패 원인을 진단하고 프롬프트를 고치는 데 뛰어나다.
6. **넓게 시작해서 좁혀라.** 짧고 넓은 검색어로 시작해서 점점 좁힌다.
7. **생각 과정을 이끌어라.** extended thinking을 계획용 메모장으로 쓰고, 도구 결과가 나올 때마다 interleaved thinking으로 평가한다.
8. **병렬 도구 호출이 속도를 바꾼다.**

방향은 엄격한 규칙보다 **좋은 휴리스틱**을 심는 쪽이다.

## 평가 (evals)

- **작게, 바로 시작하라.** 초기에는 효과가 커서 질문 **20개 정도**로도 변화가 보인다. 큰 평가 세트를 기다리지 말라.
- **LLM-as-judge:** 사실 정확도, 인용 정확도, 완전성, 출처 품질, 도구 효율로 구성된 루브릭을 쓴다. 여러 판정자보다 **한 번의 호출로 0.0~1.0 점수와 통과/실패를 매기는 방식**이 사람 판단과 가장 잘 맞았다.
- **사람 평가는 여전히 필요하다.** 초기 에이전트가 권위 있는 자료보다 SEO 콘텐츠 농장을 고르는 편향은 사람이 찾아냈다.
- **최종 상태 평가:** 상태를 바꾸는 에이전트는 과정 하나하나보다 최종 상태가 맞는지를 본다. 복잡하면 중간 체크포인트를 둔다.

## 운영의 어려움

- **오류가 누적된다.** 처음부터 다시 시작하지 말고 멈춘 지점에서 재개하게 만든다. 재시도와 체크포인트 같은 결정적 안전장치를 함께 쓴다.
- **디버깅에는 전체 추적(tracing)이 필요하다.** 대화 내용은 보지 않고 결정 패턴만 모니터링한다.
- **배포:** 실행 중인 에이전트가 깨지지 않게 rainbow deployment로 옛 버전과 새 버전을 함께 돌리며 점진적으로 옮긴다.
- **동기 실행이 병목이다.** 리드 에이전트가 서브에이전트를 기다리는 동안 조율이 막힌다. 비동기는 앞으로의 과제다.

## 긴 작업의 컨텍스트 관리 (부록)

- 끝난 단계를 요약해서 **외부 메모리**에 저장한 뒤 다음 작업으로 넘어간다.
- 컨텍스트 한계가 가까워지면 **깨끗한 컨텍스트의 새 서브에이전트**를 띄우고, 신중한 인계(handoff)로 연속성을 유지한다.
- 서브에이전트는 결과를 **파일시스템에 직접 저장**하고 참조만 넘긴다. 리드를 거치며 정보가 손실되는 "전화 게임"을 줄인다.

→ Claude Code Projects의 프로젝트 메모리, 새 스레드 생성, 라이브러리가 이 패턴과 같은 모양이다.
